# SharpForge 0.10 — symbols, live debugging, cooperative execution and WinUI web apps

This is a working development release of the JavaScript C# toolchain. All six requested extension areas have executable implementations and IDE integration. “Supported” below means the documented SharpForge managed profile, not complete CLR, Roslyn, Windows App SDK, MSBuild or Visual Studio equivalence. The last interrupted 0.10 working directory was unavailable; this release was rebuilt on the verified 0.9 source.

## Start here

```sh
npm ci --offline --ignore-scripts --no-audit --no-fund
npm start
# Open the printed local URL. No .NET SDK is needed for browser examples.
```

The prebuilt `dist/` directory can be statically hosted. `SharpForge-standalone.html` contains the IDE, compiler/runtime workers and offline editor modes. Inline scripts and Blob workers must be permitted. Native MSBuild requires the separate installed SDK/toolchain and explicit project trust; browser operation does not silently invoke native tasks.

Use **Examples → WinUI counter**, then **Window → WinUI application layout** and Run. The application remains active after `Main` returns. Press Increment to execute the C# event handler, not JavaScript substituted for that method. Stop tears down the scene and pending managed work. Other examples demonstrate controls/input, drawing and an async button handler.

The release has 20 independently installable packages and 36 independently dockable tools. The new packages are `@sharpforge/symbols`, `@sharpforge/framework`, and `@sharpforge/winui`. New tools are Symbols, Symbol Source, Threads, Parallel Stacks, Hot Reload, WinUI Application, and Visual Tree. They participate in the existing layouts, floating windows and context menus. Visual Studio remains the default editor profile.

## Portable PDBs

The symbols package reads all eight Portable PDB debug tables: Document, MethodDebugInformation, LocalScope, LocalVariable, LocalConstant, ImportScope, StateMachineMethod and CustomDebugInformation. It handles wide metadata indexes, compressed signed/unsigned sequence deltas, hidden and multi-document points, scoped local names, supported primitive constants, import definitions, state-machine associations, async stepping records and hoisted scopes. Unknown custom records retain their bytes; retaining a record does not implement every compiler-specific meaning.

Source lookup supports external bytes and embedded raw/DEFLATE source. Source Link maps can be inspected and resolved to credential-free HTTPS URLs, but no source server is fetched automatically. SHA-1/SHA-256 source verification is synchronous; the standalone API also verifies SHA-384/SHA-512 asynchronously where Web Crypto is available. Automatic debugger source binding currently uses SHA-1/SHA-256.

The compiler emits a deterministic sidecar PDB by default. Studio additionally embeds symbols and source into its output. CodeView identity (GUID plus stamp), embedded `MPDB` symbols, and the zero-PDB-ID SHA-256 checksum are checked against the exact PE. Mismatched PDBs, invalid instruction offsets, and source checksum/coordinate mismatches cannot silently become trusted source. Portable PDBs are not Windows/native PDBs.

```js
import {compileToIL} from '@sharpforge/compiler';
import {loadSymbols, bindSources} from '@sharpforge/symbols';
import {CilDebugSession} from '@sharpforge/debugger';
const build = compileToIL('int value=20;\nConsole.WriteLine(value);', {
  includeDebug: false, embeddedPdb: true
});
if (!build.success) throw new Error(JSON.stringify(build.diagnostics));
const symbols = loadSymbols(build.assembly, build.pdb);
const sourceMap = bindSources(symbols); // embedded source is checksum-verified
const session = new CilDebugSession(build.assembly, {pdb: build.pdb});
session.setBreakpoints('Program.cs', [{line: 2}]);
session.start(false);
session.runUntilStop();
console.log(session.evaluate('value').result); // 20
```

In the IDE, build and open Symbols to inspect/save a PDB and open verified read-only Symbol Source. For an ordinary DLL/EXE, use Assembly Explorer → Debug IL and load its sidecar in Symbols, or use an embedded PDB automatically. The symbol source editor is separate from project documents: inspecting another assembly never overwrites the project. Gutter breakpoints work in verified symbol source. With PDBs, direct-IL source stepping uses visible sequence boundaries; explicit instruction granularity remains available through the API/DAP.

`examples/managed/PortableSymbols.dll` is a real no-`#SF` managed fixture with sidecar and embedded symbols, generated by SharpForge. An independent Microsoft `Documents.pdb` fixture is also tested; its exact upstream blob and MIT license are retained in `tests/fixtures/portable-pdb/`. These are distinct forms of evidence. Microsoft-generated PDB reading is tested, but interoperability of SharpForge-emitted symbols with desktop Visual Studio/CLR tools has not been qualified here.

## Cooperative async and logical threads

Supported `async Task`, closed `Task<T>` and `async void` methods retain managed arguments, locals, operand stacks and cleanup continuations across awaits. The closed `T` set is int, double, bool, string and object. The framework supports the listed Task Run/Delay/Yield/FromResult/WhenAll/WhenAny contracts and cooperative Thread Start/Join/Sleep. Consult the generated API inventory for exact overloads, not the complete .NET signatures.

Task-based `Main` is awaited. `async void` is supported for event callbacks, not an async-void entry point. Method groups and the closed delegate types listed in the inventory work; arbitrary lambda syntax, general generics, arbitrary awaitable patterns, ConfigureAwait/SynchronizationContext parity and native synchronization primitives are not implemented by this release.

The compiler lowers to SharpForge's explicit continuation/capture ABI. This is **not Roslyn's generated state-machine ABI** and must not be described as general execution of arbitrary CLR async assemblies. Reading standard state-machine PDB records does not imply that such an assembly can execute in the supported VM.

Threads and Parallel Stacks show actual live/suspended logical contexts, parent/task relationships, wait dependencies and frames. Selecting a context changes inspection, not the yellow executing location. Frozen contexts can be thawed; execution is cooperative and shares one managed heap. There are no OS threads, native thread attachment, true parallel race scheduling or cross-process stacks.

Both engines expose `runAsync()`. Deterministic tests use `{virtualTime:true}`; Studio uses real delay deadlines. The scheduler bounds contexts/tasks, prunes completed unreferenced records, and traces parked frames and captured receivers through GC. Reverse snapshots retain scheduler state. Source step-out can return across an async completion to the actual awaiter instead of a different runnable context.

## Hot Reload

Pause, open Hot Reload, choose Edit code, change a compatible method body, then Apply or Apply & Continue. Cancel restores the pre-edit buffers. The running image is unchanged until a candidate compiles and validates. In a live WinUI application, event-handler changes can take effect on the next click without recreating the window or resetting static state.

Hot Reload preserves the shared managed heap, statics, compatible active-frame locals and suspended task state. Code generations are monotonic. It validates method/type/field signatures, active local/control-flow layouts and exception regions before mutation. Unsupported metadata/layout changes are rejected, rather than partially applied. Reverse history is cleared across a successful code update, and breakpoints are rebound. A stale source revision/session/code-generation request is refused.

This is in-process managed-VM method replacement, **not native CLR metadata-delta/Edit-and-Continue support**. General new types/members, arbitrary active-stack surgery, native process hot reload and unrestricted async state-machine restructuring are outside this contract. Direct IL sessions can receive a compatible rebuilt DLL through the Hot Reload panel.

## Explicit function evaluation

Automatic Watch/data tips remain side-effect-free. Immediate adds an explicitly consented invocation path that executes supported C# expressions in the selected managed frame: methods, constructors, supported operators, property getters/setters and assignments. It uses the managed compiler/runtime, not JavaScript `eval` or a host shell.

```js
session.evaluateFunction('ledger.Add(2)', {allowSideEffects: true, commit: false});
// Preview restores managed state; committing is a separate explicit operation.
```

The exact reusable entry points are exported from `@sharpforge/debugger`; Studio exposes `sharpforge.evaluateFunction`. Instruction/time limits and cancellation checks bound evaluation. Preview and failed/limited evaluation restore managed snapshots, and result handles are bounded and released on resume. Scene changes participate in rollback. Effects already delivered to external host callbacks cannot be recalled; callers should not equate managed rollback with an external transaction. Arbitrary native functions, unsupported C# syntax, blocking async evaluation, cross-process calls and every .NET framework API are not supported.

Committed evaluation captures enabled history after closing its scene-command buffer and before delivering any host command or output. A failure during this preparation restores managed state, history and buffered scene changes. Once host delivery begins, a throwing UI or output callback is reported to the caller while the evaluated state and history remain committed; earlier delivered effects cannot be rolled back. Result references stay rooted through preparation and delivery. The VM continues to reject snapshots taken while a platform transaction is active.

## Set Next Statement

At a pause, right-click a source location and choose Set Next Statement, use Ctrl+Shift+F10, or use the debugger API/DAP goto targets. Relocation changes the instruction position without rerunning preceding code or resetting locals. It is not equivalent to restarting the frame.

Validation requires the active top frame, a valid source/IL boundary and compatible empty operand stack. It rejects exception-region transitions, incompatible definite-assignment state in the source engine, stale frames/instruction counts, illegal prefixes and cross-method jumps. A reverse checkpoint can restore the prior position. Skipping user assignments can still change application behavior; this operation is explicitly requested, not automatic.

## WinUI-shaped, code-first web applications

The shared contract inventory has **79 named types and 494 ABI members**, including UI, closed task/delegate types, values and enums. Those counts are not a WinUI coverage percentage. The web host implements common Window/Application, element/control/content, StackPanel/Grid/Canvas/Border, Button, TextBlock, TextBox/PasswordBox, CheckBox/ToggleSwitch, Slider, list/combo items, progress, scroll, image, expander, navigation and flyout workflows, plus brushes and Rectangle/Ellipse/Line shapes. Properties and overloads are listed individually in [the inventory](winui-api.md).

C# object construction, properties, child/item collections, supported attached properties and method-group event subscriptions compile to a closed external ABI. The VM owns the objects, values and delegates; the browser host receives bounded scene commands and sends validated input events back. Loaded/Closed and common control events call real managed handlers. Input state is synchronized even without an explicit handler. UI objects, event delegates, arrays and suspended callbacks remain traced during collection. No missing API falls through to unrestricted JavaScript.

Use object construction inside `Main`; the current compiler does not support the complete application subclass/inheritance model. Code-first does not mean that an existing Windows App SDK DLL can be loaded unchanged. No XAML parser, WinRT/COM/native window integration, full dependency-property/style/template/binding system, all routed-event semantics, accessibility certification or pixel-exact Fluent controls are claimed. Some shape/value contracts use web-friendly representations rather than all native object types. General downcasts such as `(Button)sender` are not part of this compiler profile; examples use captured/static typed control references.

### Rendering and fallbacks

HTML controls and layout provide browser text, input, focus and accessibility behavior. Drawing surfaces and supported vector primitives have an actual WebGPU instanced-primitive shader/pipeline, with Canvas2D and DOM fallback paths. This is a hybrid host, not a fully GPU-rendered WinUI compositor. `SharpForge.UI.DrawingSurface` is a SharpForge extension, not a Microsoft WinUI class.

The renderer handles backend negotiation, size/pixel/primitive limits, resizing and fallback after unavailable WebGPU or device failure. Studio exposes a renderer selector and reports the backend/reason; it does not call a fallback “GPU”. Browser tests verify actual Canvas2D pixels and DOM fallback. This runner does not expose a usable WebGPU adapter, so physical-GPU rendering and device-loss recovery have not been qualified on hardware.

### Independent JavaScript use

`createWinUIApp(root)` returns a namespaced JavaScript facade alongside the managed bridge. Construct supported `app.Microsoft.UI.Xaml` and `.Controls` classes, assign Content/Children, subscribe handlers and Activate a window. `app.flush()`, `app.settled()` and `app.dispose()` control delivery/lifetime. This path is browser-tested separately from managed C# callbacks. It is an alternative to the managed VM, not JavaScript pretending to execute C#.

## Protocol and command line

Installed `sharpforge-dap` and `sharpforge-lsp` remain framed UTF-8 stdio servers. DAP adds real logical thread IDs, symbol-backed frames, goto/gotoTargets and explicit effectful REPL evaluation. Custom `sharpforge/hotReload`, `sharpforge/evaluateFunction`, `sharpforge/parallelStacks`, `sharpforge/freezeThread`, `sharpforge/loadSymbols`, `sharpforge/uiScene` and `sharpforge/uiEvent` requests expose the managed features. Program/PDB/source paths are explicit local-host inputs and bounded. External Visual Studio/VS Code integration has not been independently qualified.

```sh
node apps/cli/main.js run examples/projects/AsyncWorkshop/AsyncWorkshop.slnx
node apps/cli/main.js symbols examples/managed/PortableSymbols.dll
node apps/cli/main.js compile examples/projects/SymbolWorkshop/SymbolWorkshop.csproj -o symbols-demo.dll --embedded-pdb
# See `node apps/cli/main.js help` for exact compile/project forms.
```

Use `compile` with `--pdb <path>` for sidecar output or `--embedded-pdb`. CLI headless UI execution can build a managed scene but does not create a browser window. Use Studio/the web host to interact with controls.

## Validation and remaining boundaries

The release's [validation report](validation-0.10.0.md) distinguishes unit/engine tests, real browser workers, ordinary PDB fixtures, native filesystem tests, package/stdio execution, and unavailable native/GPU qualification. Browser navigation is blocked by this runner's policy, so tests load production modules into an in-memory page and create actual workers. No test-double native build result is counted as SDK success.

Read this guide together with the earlier native MSBuild, editor, docking and debugger guides. Older documents describe earlier release boundaries; this guide is authoritative for the new 0.10 features. Full C#/CLR/BCL/MSBuild/native-WinUI/Visual-Studio parity remains a larger program, not a claim made by this release.
